# AlpNile MySQL migration

هذا المجلد يحتوي على مخطط MySQL وترحيلات التطبيق. تم تنفيذ المخطط والبيانات على قاعدة Hostinger الحالية، ثم أضيفت جداول جلسات الحسابات.

## نتيجة الفحص

الموقع القديم يعمل على `https://nilea-drab.vercel.app/`، والنسخة الحالية كانت تستخدم Supabase في:

- الحسابات والجلسات والملفات الشخصية.
- الاستفسارات وحجوزات السيارات والرحلات والإقامات.
- المراجعات والإعجابات والنشرة البريدية.
- المحادثات وملفات المرفقات ولوحة الإدارة.

أما الكتالوج العام، فكان جزء كبير منه موجوداً أيضاً في كود الواجهة، ولذلك ظهرت 50 رحلة في الموقع مقابل 6 رحلات فقط في MySQL. تم توحيده الآن في استيراد MySQL رقم 003، وأصبحت صفحة الرحلات تقرأ الكتالوج من `/api/catalog?type=trips` مع إبقاء الملفات الثابتة كخطة احتياطية.

الملفات المرفقة تحتوي على 35 صفاً في 8 جداول:

| الجدول | الصفوف |
| --- | ---: |
| cities | 7 |
| trip_categories | 6 |
| trips | 6 |
| stays | 3 |
| vehicles | 4 |
| products | 3 |
| inquiries | 4 |
| car_bookings | 2 |

المخطط الكامل هنا يغطي أيضاً الجداول الموجودة في migrations الحالية: المستخدمون، الحجوزات الأخرى، الطلبات، العناصر المحفوظة، المراجعات، أسعار العملات، المحادثات وخطط الرحلات.

## التنفيذ الآمن

1. راجع `001_schema.sql` مع إصدار MySQL الذي توفره Hostinger.
2. أنشئ الجداول بتشغيل `001_schema.sql` من phpMyAdmin أو عميل MySQL.
3. ولّد ملف استيراد محلي من ملفات Downloads:

   ```powershell
   node scripts/generate-mysql-legacy-import.mjs `
     --input-dir "C:\Users\Mo Abu\Downloads" `
     --output "C:\Users\Mo Abu\Downloads\alpnile_legacy_mysql_import.sql"
   ```

4. راجع الملف الناتج، ثم ارفعه إلى phpMyAdmin وشغله داخل قاعدة AlpNile الجديدة.

## استيراد كتالوج الموقع بالكامل

الملف `003_catalog_import.sql` مولّد من مصادر الكتالوج الحالية ويحتوي على:

| النوع | العدد | الملاحظة |
| --- | ---: | --- |
| الرحلات الظاهرة في الكتالوج | 50 | 31 رحلة قديمة + 19 رحلة مضافة |
| الرحلات التحريرية المخفية من قائمة الـ50 | 7 | محفوظة للصفحات المباشرة والصفحة الرئيسية |
| المدن | 16 | مع ربط الرحلات بالمدينة الأساسية |
| التصنيفات | 14 | تشمل التصنيفات القديمة والمضافة |
| أماكن الإقامة | 6 | مع الأنشطة والمعرض داخل `metadata` |
| المركبات | 5 | مع المواصفات والصور داخل `metadata` |
| المنتجات | 30 | مع الفئة والمنشأ والخامة والصور الإضافية |

لإعادة توليد الملف بعد تعديل كتالوج الواجهة:

```powershell
node scripts/generate-mysql-catalog-import.mjs database/mysql/003_catalog_import.sql --database u700970108_alpnile
```

شغّل `001_schema.sql` ثم `002_auth_sessions.sql` ثم `003_catalog_import.sql` ثم `004_intelligence_schema.sql` ثم `005_user_profiles_notifications.sql` ثم `006_provider_operations.sql` بالترتيب. الملفات الإضافية لا تحتوي على `DROP` أو `DELETE`، وتستخدم `IF NOT EXISTS` و`ON DUPLICATE KEY UPDATE` حتى يمكن تشغيلها أكثر من مرة بأمان. يضيف الملف الثالث الحقول المنظمة الناقصة مثل السعر الفردي، الخصم، مستوى السعر، مصدر السجل، و`metadata` للتفاصيل الممتدة. يضيف الملف الرابع سجل الأحداث والتفضيلات وعلاقات الرحلات وفهارس البحث الكامل. يضيف الملف الخامس إشعارات الإدارة، بينما يضيف الملف السادس ملفات السائقين وأصحاب العقارات، التحقق الإداري، تعيينات الحجوزات، المهام المرحلية، وسجل نقاط تحديد الموقع.

يحتوي ملف `003_catalog_import.sql` على أمر `USE u700970108_alpnile` حتى يعمل أيضاً عند رفعه من صفحة Import العامة في phpMyAdmin. كما أن الرحلات والإقامات تربط المدن والتصنيفات بواسطة `slug` داخل قاعدة البيانات، وليس بواسطة UUID المولّد من المصدر؛ وهذا يحافظ على المفاتيح الأجنبية عند وجود معرّفات مختلفة في الاستيراد القديم. إذا اختلف اسم قاعدة البيانات، أعد توليده باستخدام الخيار `--database`.

السجلات الستة القديمة الموجودة مسبقاً في جدول `trips` (`food-walk` وغيرها) تبقى محفوظة في القاعدة، لكن يتم تعليمها `legacy-db` وإخفاؤها من الكتالوج العام حتى لا تتحول قائمة الموقع من 50 رحلة إلى 56 رحلة.

الأداة لا تستخدم `DROP TABLE` ولا تحذف صفوفاً. الاستيراد قابل لإعادة التشغيل باستخدام `ON DUPLICATE KEY UPDATE`، ويحافظ على معرّفات UUID الموجودة في التصدير.

ملفات `inquiries` و`car_bookings` تحتوي بيانات تواصل حقيقية، لذلك لا يتم نسخها إلى المستودع؛ الأداة تقرؤها مباشرة من مجلد Downloads وتنتج ملفاً محلياً لا ينبغي رفعه إلى Git.

## ملاحظة الصور

التصدير القديم يشير إلى صور `.png` غير موجودة على الموقع القديم (`404`). الفحص وجد أن النسخ المقابلة `.webp` تعمل (`200`)، لذلك تقوم أداة التحويل بتصحيح الامتداد من `.png` إلى `.webp` أثناء الاستيراد.

## ربط تطبيق Next.js

تم استبدال استدعاءات Supabase بطبقة MySQL server-side في Route Handlers التالية:

- `/api/auth`: التسجيل، الدخول، الجلسات وتسجيل الخروج.
- `/api/submissions`: الاستفسارات والحجوزات والمراجعات والنشرة.
- `/api/chat` و`/api/chat/upload`: المحادثات والمرفقات.
- `/api/provider`: طلبات انضمام السائقين وأصحاب العقارات، الاعتماد، التعيين، المهام ومشاركة الموقع.
- `/api/admin`: لوحة الإدارة والكتالوج وأسعار العملات.
- `/api/currency`: أسعار العملات العامة.

ضع القيم التالية في متغيرات البيئة على Hostinger، ولا تستخدم بادئة `NEXT_PUBLIC_` لمتغيرات MySQL:

```env
MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_USER=...
MYSQL_PASSWORD=...
MYSQL_DATABASE=u700970108_alpnile
MYSQL_SSL=false
MYSQL_CONNECTION_LIMIT=8
AUTH_RESET_DEBUG=false
NEXT_PUBLIC_SITE_URL=https://your-domain.example
```

بعد ضبط المتغيرات شغّل `npm run build` ثم أعد تشغيل تطبيق Node.js. حسابات Google واستعادة كلمة المرور تحتاجان إعداد مزود البريد/OAuth منفصل؛ تسجيل الدخول بالبريد وكلمة المرور يعمل مباشرة عبر MySQL.

## أدوار الشركاء

- `traveler`: المستخدم العادي، ولا يرى بيانات مقدمي الخدمة.
- `driver`: يظهر له فقط حجز السيارة المسند إليه ومهامه ومعلومات العميل اللازمة للتنفيذ.
- `property_owner`: يظهر له فقط حجز الإقامة المسند إليه ومهام تجهيز العقار ومعلومات العميل اللازمة.
- `support` و`editor` و`admin`: أدوار داخلية، مع بقاء الاعتماد والتعيين تحت صلاحية الإدارة.

يقدم السائق أو صاحب العقار الطلب من `/provider`. يبقى الطلب `pending` ولا يتم تغيير `profiles.access_role` إلى الدور الجديد حتى يعتمد المشرف الطلب من `/admin/providers`. بعد الاعتماد يمكن للإدارة ربط الحجز بالشريك وإنشاء مهمة تتطلب مشاركة الموقع. المحادثة الخاصة تتم عبر قناة AlpNile الموجودة، ولا يستطيع الشريك فتح محادثات أو حجوزات تخص مستخدمين آخرين.
